Design observations worth noting (not blockers)
section_boundary_crossed is always False in current code. chunking.py:354–355 flushes before appending a new section's paragraph, so a chunk's current paragraph list always shares one section_key, so len(section_keys) > 1 never holds. The metadata flag is dead until the chunker is taught to merge tiny sections (or it's purely documentation for downstream consumers). Spec says "如必须跨越，记录边界" — the boundary recording is wired but the "必须跨越" path doesn't exist yet. Either intentional future-proofing or remove the flag.
Title text is duplicated in text and topic. Title blocks become Paragraphs with block_type="title" (chunking.py:104–113) and get concatenated into chunk["text"] via "\n\n".join(...). The same title also lives in chunk["topic"]. Retrieval will see the title text twice — once in the body for embedding, once in the topic for metadata filtering. Could be intentional (boost section-title recall in dense search) but worth a docstring note.
chunk_id stability is fragile to incremental edits. Stable for "same input → same output", but chunk_index = len(chunks) + 1 means inserting one paragraph at page 1 shifts every subsequent chunk's index. Spec asks only for repeat-run stability and the test exercises exactly that, so this satisfies the contract — but if obj 9 plans incremental ingestion you'll want a content-derived ID component (e.g., hash of (section_key, page_start, paragraph_first_chars)).
_infer_title_level collapses sub-sub-sections to level 2. "1.2.3.4 Detailed sub" → level 2, same as "1.1 Top". The Chinese "第N节" → 2 but no "第N小节" handling. Level isn't consumed downstream yet (no test asserts level beyond truthy), so this only matters when retrieval/summary uses section level for grouping.
api_context header uses opaque section_key. [chunk_id=...; section=s0007] — LLM reads s0007 with no idea what section that is. Adding section_title to the header (truncated to ~60 chars) would help when chunks are surfaced standalone. Minor.
Multi-block paragraph split-merge is a known gap. A logical paragraph that PyMuPDF splits across two blocks (column break, line wrap) becomes two Paragraphs. Not introduced here; would surface as suboptimal chunk granularity on multi-column PDFs. Acceptable for Phase-0.
_section_paragraphs_from_dict default page_start=1. If a caller passes a section without page info, it silently becomes page 1 (chunking.py:386). Conflicts with real page-1 content. Either raise or use None + skip pages enumeration. Edge case.
No regression coverage for overlap respecting section boundaries. The overlap_tail section-guard logic is correct but isn't exercised by a test. One direct test (paragraphs across two sections → assert overlap doesn't pull from prior section) would lock it in.
