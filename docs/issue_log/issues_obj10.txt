Design observations
figures_tables.related_chunk_ids is always []. The figure-asset iterator knows which chunk surfaced each asset (logged to metadata.source_chunk_id), but the SQL column the spec mandates (related_chunk_ids BIGINT[]) is never populated. Should at minimum be [<source_chunk_id_after_resolution>]. Currently the figure→chunk relationship is dropped at INSERT time. Recommend fix before obj 11.
document_sections.parent_id is always None. section_rows groups by section_key and grabs heading/level, but never tracks the most-recent higher-level section to build hierarchy. So "1.1 Rotor Response" (level=2) has no parent linking it to "Chapter 1 Rotor Dynamics" (level=1). Schema supports the hierarchy but the data flattens to a list. Acceptable Phase-0 trade-off; flag for taxonomy/section-aware work.
chunk_type mapping diverges between Postgres and Qdrant. Postgres applies CHUNK_TYPE_MAP (body → text, formula_context → formula, etc.); Qdrant carries the raw chunk_type from the chunk dict unchanged. A retrieval filter like chunk_type=text will hit different rows in Qdrant payload vs Postgres column. Either:
Apply the same map in chunk_payload, or
Document the divergence in db/qdrant/collections.md.
SQL comment on documents.type is stale. The comment says textbook | standard | paper | review | datasheet | note. The runtime value comes from manifest.source_type, which is Literal["standard","textbook","review","paper","webpage","book","manual","note"]. So at runtime "book"/"manual"/"webpage" land in the column but aren't in the comment, and "datasheet" is in the comment but never produced. Update the SQL comment to match the Pydantic literal — otherwise future-you reads the SQL and wonders why "book" appears.
normalized_text and text collapse to the same value. SQL distinguishes them. The chunker only carries the normalized form; raw cross-page concatenation isn't preserved. chunk_row writes normalized_text=chunk["text"]. Acceptable since the source data has only one form, but the table column is now effectively redundant. Either drop normalized_text from the SQL schema or feed raw_text-derived data through chunking later.
Qdrant payload omits embedding model/version. When you eventually re-embed with a new model (bge-m3 → bge-m4), the payload won't say which model produced the existing vectors. Add embedding_model and embedding_version to the payload (and to prepare_chunk_points as kwargs). Easy now, painful later.
PostgresWritePlan carries metadata keys that aren't SQL columns. chunk_row returns a metadata dict ({chunk_id, logical_doc_id, pages, topic, source_type, section_key}), same for sections/figures/citations. The runtime writer must either drop these keys before INSERT or move them to a JSONB column. Pattern is consistent but invisible — needs a docstring at module level or a _postgres_columns registry that defines which keys are real columns.
stable_point_id uses SHA1. Deterministic, fine for now. SHA-256 truncated to 32 hex would be future-safer; not worth changing today.
No regression test for chunks with provided embeddings. Current test exercises only embeddings=None path. Adding a one-line test (prepare_chunk_points([chunk], embeddings={"doc1_p0001_00001": [0.1]*1024}) → point.vector is not None) would lock in the populated-vector path.
No multi-document test for prepare_ingestion_plan. Test uses one chunk + one document. Section deduplication across docs and seen set for figure assets are exercised but only within a single doc. Multi-doc batch ingestion is implicit through chunk_documents → prepare_ingestion_plan looping, but not tested.
document_row returns created_at: <absent> — SQL has created_at TIMESTAMPTZ DEFAULT now(). The Python row dict doesn't include the key, so the DB default fires at INSERT time. Correct, but worth documenting as "intentionally omitted to let the DB stamp it".
No mapping for documents.year and documents.authors. Both default to None/[]. Phase-0 doesn't extract bibliographic metadata. Acceptable but flag for citation/reference work later.
qa_logs has no helper. Spec doesn't list it in the obj-10 acceptance, so this is consistent with the spec. But the table exists in 001_init.sql and will need a helper when the QA pipeline writes. Track for obj 11+.


New concerns introduced by the fixes
_meta is a naming convention, not enforced by the data model. The POSTGRES_COLUMNS allowlist makes the cleanup robust regardless of key names (sql_rows() uses allowlist not blocklist) — but if you ever build a row programmatically with a typo-d real column name, it'll silently disappear from sql_rows(). Low risk; the test exercises the round-trip.
POSTGRES_COLUMNS must be hand-synced with 001_init.sql. If someone adds a column to the migration and forgets to update the registry, that column won't be written. A test that parses the SQL and compares to POSTGRES_COLUMNS would close this loop — small ask, worth adding when the schema next changes.
CHUNK_TYPE_MAP is now cross-module public API. Qdrant imports it from Postgres. Documenting this in collections.md (which you did, noting "normalized to the Postgres vocabulary") makes it explicit. If a future consumer needs a different mapping, it's a refactor candidate.
sql_rows() is currently a build-then-strip pass. Builds the full dict including _meta, then filters. For very large ingestion plans this duplicates the dicts. Negligible at Phase-0 scale; mention for obj 17 if memory becomes a concern.
