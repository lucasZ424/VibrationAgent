Critical issue — config does not flow into routing
Settings.routing exists in YAML and Pydantic, but never reaches route_task(). The bridge is missing:

route_task(policy=None) defaults to RoutingPolicy() — constructed from hardcoded class defaults, not from Settings.routing.
Same for ModelRegistry: default_model_registry() returns hardcoded model strings (gpt-5.5, claude-opus); Settings.llm.providers from YAML is independent.
So if a stakeholder edits app.yaml:

routing:
  opus_difficulties: [high, extreme]   # try to include high
Nothing happens — route_task still uses the default (Difficulty.EXTREME,) because no code reads settings.routing.opus_difficulties into a RoutingPolicy.

The test test_config_loads_gpt_first_routing_policy checks only that the YAML loads, not that the loaded values drive routing decisions. The control plane has two unrelated sources of truth right now.

Fix: Add factory methods that bridge settings → runtime models:

class RoutingPolicy(BaseModel):
    @classmethod
    def from_settings(cls, settings: Settings) -> "RoutingPolicy":
        return cls(
            gpt_owner=settings.routing.default_owner,
            opus_difficulties=tuple(Difficulty(d) for d in settings.routing.opus_difficulties),
            repeated_failure_threshold=settings.routing.repeated_failure_threshold,
            explicit_extreme_markers=tuple(settings.routing.explicit_extreme_markers),
        )

class ModelRegistry(BaseModel):
    @classmethod
    def from_settings(cls, settings: Settings) -> "ModelRegistry":
        # parse "provider:model" pairs from settings.llm.providers
        ...
Then change route_task(policy=None) to default to RoutingPolicy.from_settings(load()) when no explicit policy is supplied — or require the caller to pass one.

Other observations (non-blocking)
app.yaml has two parallel role schemes. New roles (interaction_main, task_router, executor, senior_planner, senior_reviewer, emergency_owner) coexist with legacy (main_answer, coder, reviewer, citation_checker). Nothing in code reads the legacy ones. Either remove them or mark as deprecated comments.
route_task overwrites reason on each rule trigger. The final reason reflects only the last applied rule. For audit/observability, capture the reasoning chain (e.g., reasons: list[str]). Currently you can't tell from the decision whether a task became EXTREME via explicit marker vs. repeated-failure threshold.
RoutingPolicy.opus_difficulties: tuple[Difficulty, ...] vs RoutingSettings.opus_difficulties: list[str]. Different sequence types and different element types for the same data. Resolved automatically by Pydantic on construction but the type signatures are inconsistent. Pick one (likely tuple+Difficulty for runtime, list+str for config).
AgentSkillRegistry.load() paths are relative to CWD. Stored as Path("agent_skills/s1_ingestion/SKILL.md"). Works from project root but breaks if invoked from elsewhere. Either resolve to absolute at load time, or document the CWD assumption. The test only passes because pytest runs from project root.
AgentSkillRegistry has no validation that referenced runtime skill exists. Loading s1_ingestion/SKILL.md doesn't check that vibration_agent.skills.s1_ingestion.IngestionSkill is importable. A drift between the markdown and the Python wouldn't surface until runtime. Optional: cross-check in load() or in a separate test.
SupervisorAction.OPUS_TAKEOVER is a return value with no executor. Schemas-only is correct for obj 11.5; flag for whichever future objective wires the runner.
default_model_registry() hardcodes gpt-5.5 and claude-opus. Real model names will surface in obj 17+ when API clients are added. The strings are placeholders; the structure is sound.
scripts/run_s1_ingestion.py is a no-op re-export. Doesn't have if __name__ == "__main__". Cosmetic — either add a CLI runner or delete and just have SKILL.md point to vibration_agent.skills.s1_ingestion:IngestionSkill as the entry point.
_explicit_extreme matches markers exactly (marker in marker_values). A free-text marker like "route: extreme review" won't match "extreme" because the value isn't exactly "extreme". Substring match would be more permissive; acceptable for Phase-0.
No multi-skill registry test. AgentSkillRegistry.load() is exercised with one skill. The sorting + multi-skill as_prompt_catalog order isn't tested. Low risk.
